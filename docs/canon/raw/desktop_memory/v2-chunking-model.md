**The v2 chunking/structure model, converged with the user 2026-06-01.** Refines the chunk/structure step of [[v2-build-pipeline]]. Replaces v1's chunker (per-record for generic data, hardcoded per-section budget-batching for HERB, only Slack grouped meaningfully — by channel).

## Decisions
1. **A chunk = a coherent episode, NOT a fixed-size window.** Kill v1 fill-to-budget batching (it smears the v2 facets, which only mean something on a coherent unit — coherence is now load-bearing in a way it wasn't for v1's shallow keyword tags).
2. Build chunks by **descending the source's own structure**, then group leaf-level conversation/prose by coherence.
3. **Token budget = guardrail/ceiling only**, never the grouping rule. The number is trivial; pick later.
4. **Over-budget episode → splits into subchunks that ARE just chunks** (`1` → `1.1`, `1.2`, `1.3`). NO parent node, no episode node — the episode exists only as "the chunks sharing a path prefix," reconstructed on demand at query time. (User killed the parent explicitly; I kept overbuilding it.)
5. Split priority: **finest coherence seam first**, blunt size cut only at the floor.
6. **Index = materialized path stored as integer components** (`[1,2,3]`, not the string `"1.2.3"` — so `1.10` doesn't missort and prefix-match stays clean). Replaces the flat `ordinal` + `NEXT` that v1 chunks have now. Runs the whole way down: file → structure → episode → subchunk. It's a generalization of `ordinal`, not a new concept.
7. **Path carries POSITION only.** Meaning/type of each level (channel/section/message) lives in the probe's recovered shape schema — path says *where*, schema says *what*. Don't cram type into the numbers.
8. Path does **triple duty**: structural ancestry, context expansion (gather by prefix), duplicate-collapse/diversity (group by prefix).
9. **"Records vs prose" is per-POSITION in the tree, not a per-file classification.** Walk the tree: regular structured parts → addressable positions (references + hard-field values as chunk attributes; NO record nodes — [[v2-graph-spine]]); long-text leaves (incl. a prose field *inside* an otherwise-structured record, e.g. HERB doc/transcript = metadata fields + content field) → coherence-chunked. Binary/opaque → reference only, no fake decomposition. Most real data is MIXED.
10. **Context comes from the graph around the chunk** (small-to-big / parent-record, like Anthropic's contextual-retrieval but free from structure), NOT from fat chunks or overlap. **No overlap** — it fights references-not-copies; the same record in two chunks would be double-tagged, double-attributed, double-surfaced.
11. **The boundary detector is fully DETERMINISTIC — no embeddings, no LLM.** It's one seam-finder run top-down: the same mechanism does first-pass episode segmentation AND recursive over-budget splitting, just at finer scale. It only matters for ONE case — a flat conversational stream with no thread structure (explicit threads → group by thread; structural records like a PR+reviews → the record IS the unit; prose → splitting, a different problem). Seam ranking, most-reliable+cheapest first: explicit reply/quote link (works AGAINST cutting — never split two linked messages) > day boundary / large time-gap > participant turnover. The time-gap is **adaptive/relative** — a seam = a gap much larger than the *local* typical gap (median × k), NOT a fixed minutes constant (channel pace varies wildly) — with a fragment floor (no 1-message shards) and the budget ceiling as the forced-cut backstop. **Topic-drift / embedding-similarity REJECTED as a boundary signal** (the assistant invented it mid-conversation; never in the docs): it's circular (nothing is embedded at chunk-time — the chunk is the unit you're forming), would need an extra pre-pass embedding every raw message, and terse chat ("+1", "see above") embeds to noise. Boundaries are decided at structure-time, before the embedder/tagger touch anything.

## Research grounding (the user asked for it)
- Most chunking research is about *splitting* long prose; the user's hard case is the opposite — *grouping* tiny discrete records. Maps onto conversation/topic segmentation, not document splitting.
- Semantic (embedding-similarity) chunking is NOT a reliable win — the 2024 "Is Semantic Chunking Worth the Computational Cost?" paper found it rarely beats simpler structural splitting enough to justify cost. For record data, the structure (threads/reply links/message boundaries) is a better+cheaper signal.
- Hierarchical / small-to-big / RAPTOR-adjacent — but explicitly DON'T summarize parents (RAPTOR does; that recreates copies-not-references).
- "Late chunking" (Jina 2024) is in-pocket for the long-text path only: the embedder takes 8k tokens, so embed whole doc then pool per-chunk vectors → each chunk embedding remembers its document.

12. **The materialized path is canonical structure top-to-bottom — records INCLUDED; the ONLY non-canonical positions are subchunk fragments** (resolved with the user 2026-06-03 — this settles the old "handoff-depth" question, which turned out to be a non-question). A record's path component and its json_pointer are two views of the SAME canonical source spot, so there's no second drift-prone address. There is no fixed structure→chunk handoff depth: the path mirrors the source the whole way down. A split is the one place we mint positions the source doesn't have, and it **inserts a non-canonical tier**: over-budget thread `[1,2]` → fragments `[1,2,1]`, `[1,2,2]`, `[1,2,3]`, and its messages ride one tier deeper as canonical leaves beneath them. Records are NOT exiled off-path (the assistant's first framing, which the user corrected) — they sit ON the canonical path; the chunk→records join is the path prefix + the chunk's references (no COVERS edges, no record nodes — [[v2-graph-spine]]).

13. **The budget number IS the tagger's effective focus span — cap ≈ 3000 tokens** (resolved 2026-06-04; vs v1's 800 target / 1500 hard). NOT a token-count-for-its-own-sake and NOT an embedder limit (the embedder only ever sees short artifacts — the phrase tags — never raw chunk prose). Deliberately *larger* than the classic RAG 512–1024 band because v2 never embeds the raw chunk: meaning lives in the union of the chunk's phrase tags (NO description — dead 2026-06-11), so there's no fat single-vector to dilute (the usual small-chunk advice is downstream of single-vector compression, which we sidestep). 3000 is a calibration SEED — sweep size vs tag relevance, set the cap just under the knee. **Split rule (uniform; supersedes the fragment-floor/min in #11):** unit from structure → if it exceeds the cap, walk back to the BEST natural seam in the window (strongest, not nearest) and recurse; NO minimum size (a unit under the cap is already a chunk); worst-case seam is always a sentence/EDU, so never a butcher cut. **Seams are per content-kind** (chat: reply/adjacency-pair > adaptive time-gap > turnover > lexical-topic; prose: section>paragraph>sentence/EDU; records: record boundaries), dispatched by probe shape, NOT file format. **Data model (revised 2026-06-11/12):** tags are per-chunk phrase nodes — the contextual phrase + its embedding ON the node; intrinsic values on the node, sibling-relational values on the chunk→tag edge; the old shared-Tag-node + description-embedding placement is DEAD — see [[v2-graph-spine]] and [[retriever-routing-model]]. Literals kept alongside embeddings, nothing replaced. Grounded: TextTiling/RST/conversation-analysis (linguistic), "Is Semantic Chunking Worth the Cost?" + conversation-disentanglement (data), RULER/NoLiMa effective-context (LLM).

14. **The tagger is one stateless call per chunk** (resolved 2026-06-08) — single structured-output invocation, temp 0, one chunk in / phrase tags out (no description, no numbers), instance discarded; NOT an agent loop, NOT chunks batched per call. Context comes in as an explicit graph-assembled *input* (pure function of chunk+graph → reproducible), never instance memory. This statelessness is the **PRECONDITION** for the whole build-time validation strategy ([[tagger-build-validation]]): golden tests, response-caching, small-sample error-analysis, and prompt-regression assertions are valid only because the sole variable across runs is the prompt — none hold against a stateful order-dependent agent. Same commitment as the #13 cap (one coherent chunk, one focused fresh instance); batching chunks per call would violate both the focus-span premise and reproducibility. Folded into design doc §9.5.
