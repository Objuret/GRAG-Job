# Verification

## 1. Audit of the `harness_template` rule (largest reject bucket)

`harness_template` is the only rule that inspects text rather than structure, so
it is the only place a real human turn could be silently discarded. Audited
three ways.

**A. Complete enumeration in the conversational directory.** The headless
directory is machine-only by measurement (below), so every possible false
negative lives in the 38-file conversational directory. That set is small enough
to enumerate in full rather than sample: **9 turns**, all machine:

| turns | text | why it is not human |
| ---: | --- | --- |
| 8 | `reply with exactly: OK` | eight identical single-turn sessions fired 2026-07-17 12:16:09-12:17:30, one per model, each its own session with zero tool activity - the headless model-availability probe recorded in memory for that date |
| 1 | `Context: "The quarterly report was written by Ana Torres." ... Reply ONLY JSON: {"verdict": 1 or 0}` | RAGAS faithfulness judge smoke test |

**B. Stratified sample of the headless directory.** 74 turns sampled across all
10 (month x template) buckets, proportional to bucket size. Every one is a
harness prompt: RAGAS metric prompts (statement generator, context recall,
faithfulness, answer correctness), the RAGAS output fixer, the tagger
(`Documents:`), the tag scorer (`Original query: ... Score these tags:`), the
query interpreter (`User query:`), and the evidence walk
(`Question: ... Evidence so far (top N):`). Zero conversational turns.

**C. Risk screen.** Every `harness_template` reject shorter than 400 characters
that contains no JSON or structured markers - the shape a human turn would have
- was pulled out: 966 turns, all of them HERB benchmark questions carried by the
`User query:` and `Original query:` templates. Zero conversational turns.

**False-negative rate: 0 of 6,380 (0.00%).** No fix required. The rule is
prefix-anchored and the two prefixes a human could plausibly type (`Context:`,
`Question:`) are both additionally gated on a machine-only substring
(`Reply ONLY JSON`, `Evidence so far`).

## 2. Shape of the corpus - why 6,420 files yield only 28 sessions

Every file was classified by what its user turns actually are. Derivation: run
the filter over each file; a file with >=1 surviving turn is interactive, a file
whose turns are all `harness_template`/`headless_directory` is a headless
model-call session, a file with no user record at all is a stub.

| class | files | derivation |
| --- | ---: | --- |
| headless model-call sessions (v3 dir) | 6,372 | one templated prompt per session, no second human turn anywhere |
| `ai-title` stubs (v3 dir) | 10 | single-line files containing only a generated session title, no user record |
| interactive sessions (root dir) | 29 | contain at least one surviving human turn |
| headless model-call sessions (root dir) | 9 | the 8 model probes + 1 judge smoke test from rule audit A |
| **total** | **6,420** | |

**Subagent/sidechain transcripts: 0.** No record in either directory carries
`isSidechain: true`. This Claude Code version does not persist subagent
conversations as separate transcripts - agent work survives only as tool results
inside the parent session and as `tasks/*.output` files under the temp
directory. The `sidechain` rule is therefore implemented but never fires here.

The 6,372 headless sessions are the evaluation harness itself: each RAGAS metric

## 5. The 90 collapsed duplicates were true duplicates

- **uuid collisions: 0.** Claude Code regenerates uuids when a session is
  branched, so the uuid pass never fires on this corpus. All 90 collapses came
  from the secondary `(timestamp, text)` key.
- All 90 are **cross-file**, never within a file (within-file collapses: 0).
- Every pair sits between sibling sessions that begin at the same instant -
  `05c4a4e4`/`1ccd9ede`/`6f8beb42`/`ded2c8da` all open 2026-07-24T23:21:23.887Z,
  `2e12d748`/`559c151a`/`96031fa3`/`a63871ed` all open 2026-07-29T23:07:20,
  `11c068bc`/`cf5e5327` both 2026-07-22T01:16:56, `69789442`/`ed7d2b13` both
  2026-08-01T10:28:18. These are resume/branch copies of one conversation.
- Timestamps match **to the millisecond**. A human cannot type the same text
  twice in the same millisecond, so identical text at an identical millisecond
  is a replayed record, not a second message.

**The rule does not over-collapse.** Repeated short commands survive whenever
they are genuinely separate messages: `continue` appears 29 times in the output,
`doit` 6 times, `soo..` 4 times, each with its own timestamp. The strongest case
is the same 600-char paragraph sent twice 33 seconds apart
(2026-07-25T00:03:11.360Z and 00:03:44.443Z) - both retained, because the key
includes the timestamp.
