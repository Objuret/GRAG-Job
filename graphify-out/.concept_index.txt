v3_readme_construct_validity	Caveat worth remembering: answer-level scoring measures the whole pipeline not retrieval alone — a strong generator can mask retrieval quality — so the deterministic context precision/recall is what keeps an endpoint pointed directly at retrieval, the artefact's actual claim.
v3_readme_contract_shared_shapes	contract.py holds the shared shapes everything imports (QuestionWithTruth, ModelUsage, ArmOutput, BuildStats, EvalResult, RunManifest, EvalManifest).
v3_readme_data_quarantine	The data split is a quarantine: data/corpus/ has the oracle stripped and pipelines see ONLY this via a truth-free prompt, data/raw/ holds full HERB (~1514 questions + ground_truth + citations inside the product files) read by evaluators in place, and metadata/ (employee/customer/team) stays on both sides as legitimate retrieval data.
v3_readme_deterministic_id_context	The deterministic RAGAS backbone is ID-based context precision/recall against the gold citations (IDBasedContextPrecision / IDBasedContextRecall, no judge); the judged picks are faithfulness, answer correctness, context precision and context recall.
v3_readme_doc	v3/README.md — the in-repo canon design reference for the v3 HERB evaluation harness: three arms (artefact/lucene/vector), one shared generator, shared corpus on disk, scored with RAGAS.
v3_readme_faithfulness_transfers_no_gold	Faithfulness needs no reference so it transfers to a no-gold set later; the other three judged metrics (answer correctness, context precision, context recall) lean on the gold answer / citations.
v3_readme_generator_neutral_pipe	Generation contract — a thin fixed RAG pipe: one fixed system instruction ("Answer the question using only the provided documents. Be concise.") then the question exactly as posed plus the arm's retrieved passages as a labelled user turn, taking back a structured {answer}; generic grounding not retrieval engineering, held byte-identical across all three arms so the only variable stays retrieval; any thin/empty-context handling is an individual arm's own concern.
v3_readme_gold100_set	build_question_sets.py writes id-set views (full/answerable/unanswerable, 1514/815/699) plus the gold-100 — a balanced answerable subset drawn by seeded round-robin over HERB types (equal allocation ~20/type); equal allocation keeps every type usable per-type but does not match HERB's natural mix, so report per-type and don't compare the gold-100 aggregate to HERB's published average.
v3_readme_lucene_arm	The lucene arm is built on bm25s method="lucene" (the Lucene/Elasticsearch BM25 variant, k1=0.9 / b=0.4 BEIR reference values) reproducing Lucene's scoring exactly with Lucene-like EN-stopword + Snowball/Porter2 analysis; one document per artifact, artifacts-only index justified because all 17,087 gold citations resolve to an artifact id.
v3_readme_nim_transport	nim.py is the one NVIDIA NIM REST transport through which generator, embedder and judge all POST — shared harness plumbing, not retrieval code.
v3_readme_one_llm_generator_and_judge	One LLM serves as both generator and judge — qwen/qwen3.5-397b-a17b on NVIDIA NIM; multilingual so HERB now and the deferred Swedish Bonnier set run on the same model, and being not GPT-4o means HERB's published baselines are re-run, not cited.
v3_readme_one_shared_generator	All three arms answer with the SAME generator (built once in the orchestrator and injected) so any difference is retrieval, not the LLM; beyond that generator and the corpus on disk the arms share nothing — each reads, indexes and ranks the corpus with its own code, sharing no retrieval code.
v3_readme_oracle_free_record	The questions run record carries no oracle (one oracle-free row per question, appended as it goes so a crash keeps what finished), so you can read it and see the quarantine held; a hard error fails loud and stops.
v3_readme_orchestrator_role	orchestrator.py owns the shared generator, runs an arm through generation and a scorer through evaluation, and writes the manifests; it currently runs a single combined path and splitting it into the three modes is the pending step.
v3_readme_question_ids_minted	Question ids are minted deterministically (HERB ships no native id): <product>::a|u::<index> from (product file, array, position), 815 answerable + 699 unanswerable = 1514 unique, the paired-test join key; questions.load_questions hydrates QuestionWithTruth from raw with an exact id filter that raises on an unmatched id.
v3_readme_ragas_only_scorer	RAGAS (eval/ragas.py) is the only scorer; the full RAGAS metric menu lives in eval/ragas_catalog.py — every judge-free deterministic metric always runs (costs nothing) and SELECTED adds the judged ones.
v3_readme_raw_per_question_records	RAGAS emits raw per-question records (EvalResult, tidy long format) with nothing pre-aggregated, so paired tests, CIs, per-type splits and judge calibration are all possible downstream.
v3_readme_split_telemetry	Per-question telemetry is split: ArmOutput.generator (the shared answer-writer, identical across arms) versus ArmOutput.retrieval (the arm's OWN retrieval-time model cost — vector's query embed, zero for lucene).
v3_readme_still_open	Still open: the orchestrator split into questions/evals/full modes with per-run-folder run identity, the top-k budget value, which set to run (gold-100 vs the full 815+699), and the judge-calibration subset size.
v3_readme_three_arms	The harness runs chosen HERB questions through three arms — artifact (the artefact graph: interpreter → facet retrieval → answer, system under test), lucene (BM25 baseline, own index), vector (dense naive-RAG baseline, own index) — and scores each arm's answer with RAGAS.
v3_readme_two_manifests_provenance	Each run writes a RunManifest (arm, generator model, top-k, questions file, n, timestamp, build stats) on the generation side and an EvalManifest (scorer, judge model, source run, arm, timestamp) on the scoring side; no seed, no git-sha.
v3_readme_two_phase_run_flow	Generation and scoring are split into two separate phases (modes questions / evals / full) so iterating a scorer never re-runs the LLM; the questions phase answers chosen questions writing an oracle-free records.jsonl + run_manifest.json, the evals phase re-joins truth by id and writes eval_results.jsonl + eval_manifest.json.
