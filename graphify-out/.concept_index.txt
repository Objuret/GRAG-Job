v3readme_evals_mode	`evals` mode — one scorer reads a run folder and scores it: read records.jsonl → re-join truth (type, ground_truth, citations) by id from `data/questions.jsonl` → `score_outputs` → one `EvalResult` per (question × metric) → eval_results.jsonl and eval_manifest.json
v3readme_files_map	File map: `contract.py` holds the shared shapes everything imports (QuestionWithTruth, ModelUsage, ArmOutput, BuildStats, EvalResult, RunManifest, EvalManifest); `nim.py` is the one NVIDIA NIM REST transport that the generator, embedder and judge all POST through — shared harness plumbing, not retrieval code; `pipelines/` holds `artefact_v1.py` and `artefact_v1_det.py` (the arm under test and its interpreter-free leg), `lucene.py`, `vector.py`, `hybrid.py`, and `artefact.py` (the native rebuild's arm entry); `eval/` holds `ragas.py` and `ragas_catalog.py`; `orchestrator.py` owns the shared generator, runs an arm through generation and a scorer through evaluation, and writes the manifests; `smoke.py` is a tiny wiring check; `data/` holds `corpus/` and `raw/`, `output/` holds results as per-run folders with `smoke/` for checks
v3readme_goal	Goal: run the chosen HERB questions through the arms, get an answer from each, and score those answers with RAGAS. v3 is the eval harness for comparing the artefact against baselines on HERB
v3readme_gold100	`build_question_sets.py` writes the `{id, type, question}` id-set views to `output/` — full / answerable / unanswerable (1514 / 815 / 699) — plus `question_ids.gold100.jsonl`, the gold-100: a balanced answerable subset drawn by seeded round-robin over the HERB types (equal allocation, ~20/type). Equal allocation keeps every type usable per-type; it does not match HERB's natural mix, so report per-type and do not compare the gold-100 aggregate to HERB's published average. Point the orchestrator's ids-file at whichever view you run
v3readme_interpretation_not_intent	v3/README.md opens by declaring itself interpretation, not intent: agents' claims about how the harness should work, written over months, and being written there is not the user's approval. Intent lives only in the user's own typed turns (`docs/canon/raw/user_turns*`); state lives in the git history and the code and is evidence of drift from intent, never justification for it. `docs/canon/CANON_AUDIT.md` checks 117 prescriptive claims across the repo's instruction surfaces — 65 grounded in a user quote, 17 agent-origin, 11 contradicting the record, 24 stale — of which 12 come from this file; that audit is interpretation too and unreviewed, and both files are listed `unreviewed` in `docs/canon/REVIEW_REGISTER.md`
v3readme_judged_picks	The judged picks are faithfulness, answer correctness, and context recall. `context_precision_llm_ref` stays commented out because it is ~k judge calls per question and turns the slow lane into the whole run. Faithfulness needs no reference, so it transfers to a no-gold set later; the other judged metrics lean on the gold answer and citations
v3readme_manifests	Each run writes a `RunManifest` (arm, generator model, top-k, questions file, n, timestamp, build stats) and an `EvalManifest` (scorer, judge model, backend, reasoning effort, aggregate judge usage including reasoning tokens, source run, arm, timestamp) for reproducibility
v3readme_quarantine	Data split — the quarantine: `data/corpus/` has the oracle stripped out and pipelines see only this, and only via a truth-free prompt; `data/raw/` is full HERB, where the ~1514 questions plus ground_truth plus citations live inside the product files and evaluators read truth in place; `metadata/` (employee / customer / team directories) stays on both sides because it is legitimate retrieval data, not oracle
v3readme_question_ids	Question ids are minted deterministically because HERB ships none: `<product>::a|u::<index>` from (product file, array, position) — 815 answerable + 699 unanswerable = 1514, unique, and the paired-test join key. `build_questions.py` writes the full set (`{id, question, type, ground_truth, citations}`, a/u lives only in the id) to `data/questions.jsonl` and `questions.py` loads it; `questions.load_questions` hydrates `QuestionWithTruth` from raw and the id filter is exact — an unmatched id raises
v3readme_questions_mode	`questions` mode — one arm answers the chosen questions: load chosen questions (truth from raw) → open corpus → build the shared generator → prepare the arm once (→ BuildStats), then per question (id + text only) → `arm.answer_one_question` → `ArmOutput(answer, contexts, context_ids, search_time_s, generator, retrieval)` → a per-run folder with records.jsonl (one oracle-free row per question) and run_manifest.json. Rows append as they go so a crash keeps what finished; a hard error fails loud and stops
v3readme_ragas_scorer	RAGAS (`eval/ragas.py`) is the scorer; the full RAGAS metric menu lives in `eval/ragas_catalog.py`. Every judge-free (deterministic) metric always runs because it costs nothing, and `SELECTED` adds the judged ones
v3readme_raw_records	RAGAS emits raw per-question records (`EvalResult`, tidy long format) with nothing pre-aggregated, so paired tests, CIs, per-type splits and judge calibration are all possible downstream
v3readme_shared_generator	Every arm answers with the same generator, built once in the orchestrator and injected, so any difference is retrieval, not the LLM. Beyond that generator and the corpus on disk, the arms share nothing — each reads, indexes and ranks the corpus with its own code (how it does so is what the comparison measures); they share no retrieval code with each other, and nothing with the artefact
v3readme_still_open	Still open: the orchestrator split into the three `questions` / `evals` / `full` modes with a per-run-folder run identity, so a gold-100 run and a full run do not clobber (the orchestrator runs a single combined path); a matched-character-budget comparison at n=100 — the only one that exists is the `__b72000` family on 10smoke (n=10) and it binds the artefact arm alone, while the 500-id runs match ids exactly and characters not at all; which set to run — gold-100 (built, seeded stratified draw) against the full 815 + 699; and the judge calibration subset size that validates the judged RAGAS metrics
v3readme_system_under_test	The system under test is the modified v1 artefact, querying the `herb-eval` graph: `pipelines/artefact_v1.py` plans with a model, `pipelines/artefact_v1_det.py` plans deterministically. They are two configurations of it, not baselines, and both are reported — neither is the artefact's single result, and every figure names its leg. The ruling and what it forbids are in `CLAUDE.md` §"Artefact arm", the numbers under it in `output/DATA_README.md`
v3readme_two_phases	Generation and scoring are two separate phases, so iterating a scorer never re-runs the LLM. Three modes: `questions`, `evals`, and `full` (the two back to back). The run record carries no oracle, so you can read it and see the quarantine held
