# HERB three-arm evaluation — data shipment notes

One retrieval experiment, three arms over the same 100 questions (`gold100.jsonl`),
k = 50 contexts per question, one shared answer schema. Each run dir holds
`arm_outputs.jsonl` (answers + retrieved contexts + per-question token/time
usage), `eval_results.jsonl` (one row per question × metric), and manifests.

For cross-arm judged metrics use the three haiku-judged dirs (artefact +
the two `__j-claude-haiku-4-5` re-judges): same judge everywhere. The June
canon-judged results remain valid as a second judge's opinion; a 10-question
4-judge agreement study (`__n10` dirs) measures inter-judge distance
(haiku↔canon mean |Δ| per cell: 0.00–0.15 depending on metric).

## Metric validity — read before comparing

| metric | cross-arm validity |
|---|---|
| `context_recall_id` | **valid** — exact: gold citation ids found among retrieved ids; denominator is the gold set, identical for every arm |
| `faithfulness`, `answer_correctness`, `context_recall_llm` | **valid within one judge** — use the haiku-judged trio; note the generator confound below |
| `context_precision_id` | **NOT cross-arm comparable** — denominator is every id carried by retrieved chunks, and chunk id-density differs per arm (~500 ids/question artefact, ~50 baselines) |
| `context_precision_nonllm`, `context_recall_nonllm` | **NOT cross-arm comparable** — string similarity of context text vs gold context text penalizes the artefact's raw-JSON context format regardless of content |
| `semantic_similarity`, `chrf`, `string_similarity`, `rouge`, `bleu` | weak here: gold answers are entity lists, answers are prose; treat as noise floors |
| `exact_match`, `string_presence` | dead on this data (0.000 / near-0 for every arm) |

## Known properties of the benchmark and runs

- **Generator confound (judged/answer metrics only):** artefact answers come from
  claude-sonnet-5, baseline answers from qwen3.5-397b. Retrieval id-metrics are
  unaffected (computed from retrieved ids, not answers).
- **gold100.jsonl composition** is 22 person / 55 content / 17 pr / 5 company /
  1 url — not the equal 20-per-type draw `build_question_sets.py` produces; its
  original draw predates the current question file. Per-type numbers for company
  (n=5) and url (n=1) are anecdotes.
- **Company questions are two-hop joins.** Products files name customers only as
  `CUST-` ids; `metadata/customers_data.json` maps ids → company names. The
  lucene and vector arms index `products/` only and structurally cannot answer
  them; the artefact arm indexes metadata but did not retrieve the mapping chunk
  for any of the five. All arms score ≈0 on company-type judged recall.
- **Recall ceilings:** gold citation sets average 39 ids (max 254); questions with
  more than 50 citations cannot reach recall 1.0 at k = 50. Identical ceiling for
  every arm.
- **Token accounting eras:** June runs record one legacy `tokens` total (reported
  as input); the artefact run's claude-lane counts exclude cache-read tokens, so
  its recorded generator input (280) massively undercounts the real ~9M. Output
  token counts include model reasoning where the backend bills it.
- **Timing fields:** per-call timers include queue/stall time. The artefact run
  waited out an exhausted API budget mid-run; its per-call max times (~8 h) are
  stall, not compute. Medians are representative (interpret ≈ 20 s, generate ≈ 28 s).
- **Judge-side cost is unrecorded:** judge token usage was never persisted for any
  eval in this shipment.
- `artefact_v1…/run_manifest.json` `generator_model` was restored to
  `claude-sonnet-5` on 2026-07-20 after an eval-only resume had overwritten it
  with the config default; the answers themselves were never regenerated.
- Vector June `eval_manifest.json` has `judge_model: null` — it predates judge
  provenance recording; its judge was the canon qwen3.5-397b.
